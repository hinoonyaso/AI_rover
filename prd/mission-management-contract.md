# 모의 임무 저장·API 계약

상태: 구현용 설계(2026-11-15). 이 문서의 DB 테이블·API·작업자는 아직 구현되지 않았다. 기존 입력 검증과 전이는 `tools/ops/backend/mission_contract.py`가 구현 원본이다. 실제 로봇 실행·ROS 명령은 이 계약에서 허용하지 않는다.

## 범위와 책임

단일 Mission Manager가 임무 및 상태 이력의 소유자다. API는 요청을 검증해 관리자에 전달하고, 화면은 응답을 표시한다. 최초 모드 `simulation`의 `inspection_demo`는 빈 `parameters`를 가진 순수 모의 임무다. 점검 장비·위치·ROS 기능이 동작한다는 뜻이 아니다. 관리자는 로봇 연결 없이 별도 프로세스 또는 명시적으로 단일 소유가 보장된 프로세스에서 실행하며, 일반 FastAPI 다중 worker마다 하나씩 기동하지 않는다.

## 데이터 계약

모든 새 시각은 UTC로 저장·응답한다. 연결 세션의 시간대는 UTC로 설정하며, 문자열에는 `Z` 또는 명시적 `+00:00`을 붙인다. 기존 지표·이벤트 테이블 시각과 혼동하거나 그 테이블을 변경하지 않는다. 데이터 형식과 제한은 구현 시 DB 및 API 양쪽에서 검증한다.

| 테이블 | 필드 | 제약·의미 |
|---|---|---|
| `missions` | `id` UUID, `request_id` UUID | ID 기본키; 생성 요청의 `request_id`에 고유 제약. 소문자 표준 UUID 문자열. |
| | `mode`, `kind`, `parameters` | 초기 값은 `simulation`, `inspection_demo`, 빈 JSON 객체만 허용. 저장 후 불변. |
| | `state`, `stage`, `version` | 상태는 코드의 `MissionState`; 단계는 모의 실행기 정의값 또는 null; `version`은 생성 시 1, 상태나 단계가 바뀔 때 1씩 증가. |
| | `created_at`, `started_at`, `finished_at` | UTC. 시작 전 `started_at` 및 종결 전 `finished_at`은 null. |
| | `result`, `reason` | JSON 결과 또는 null, 기계 판독 가능한 이유 코드 또는 null. 모의 결과임을 `mode`로 구분. |
| `mission_events` | `mission_id`, `version` | `(mission_id, version)` 고유; 임무 외래키. 생성 자체도 첫 이벤트(version 1)로 기록. |
| | `previous_state`, `state`, `stage` | 이전 상태는 생성 이벤트에서만 null. 단계 변경도 이벤트로 남긴다. |
| | `recorded_at`, `source`, `reason`, `details` | UTC, 출처·사유·상세. 요청·토큰·민감한 입력 원문을 기록하지 않는다. |
| `mission_execution_slot` | 고정 ID 1, `mission_id` | 임무 관리자 실행권을 보호하는 단일 행. 임무 점유와 상태 전이를 같은 DB 트랜잭션에서 수행한다. 빈 슬롯은 null. |

생성 요청과 첫 이력, 상태/단계 변경과 이력, 활성 슬롯 변경은 각각 하나의 트랜잭션으로 묶는다. 상태 전이는 `mission_contract.py`의 허용 목록에 따르고 `UPDATE ... WHERE id = :id AND version = :expected_version`의 결과 행 수를 검사한다. 성공한 변경에만 버전을 올리고 같은 버전의 이벤트를 삽입한다. 종결 상태로의 갱신과 슬롯 반환도 함께 커밋한다. 부분 쓰기는 롤백한다.

스키마는 별도 비파괴 migration으로 새 테이블만 생성한다. 운영 DB 적용 전 백업과 격리 사본 복구를 검증한다. MySQL의 DDL은 자동 커밋될 수 있어 migration 전체가 원자적이라고 가정하지 않는다. 중간 실패 시 기존 객체 구조를 검증하고 안전하게 재실행한다. 기존 테이블 삭제·수정, 개발용 fixture의 운영 DB 삽입은 하지 않는다.

## 중복 요청과 동시 실행

- **생성**: 클라이언트의 `request_id`를 멱등 키로 사용한다. DB 고유 제약으로 동시에 같은 키가 들어와도 임무는 한 건만 생성한다. 검증·정규화된 `mode`, `kind`, `parameters`가 기존 요청과 같으면 동일 임무를 반환하고, 다르면 `409 idempotency_conflict`를 반환한다. 중복 요청은 새 이벤트를 만들지 않는다. 요청의 만료나 임무 삭제 정책은 이 단계에서 도입하지 않는다.
- **시작**: `created`에서만 가능하다. DB 트랜잭션에서 단일 슬롯 행을 잠그고 미점유일 때 슬롯을 점유해 `queued` 전이를 기록한다. 이미 점유되어 있으면 `409 mission_busy`; 미확정 트랜잭션이 있으면 락 획득 후 상태를 재확인한다. 슬롯 미점유로 이미 종결된 임무는 재시작하지 않는다.
- **시작 재시도**: 같은 임무가 이미 `queued`/`running`일 때 중복 실행을 만들지 않고 현재 상태를 반환한다. `cancel_requested`나 종결 상태는 `409 invalid_transition`이다. 이 작업은 같은 임무 ID에 한해 멱등이며, 같은 ID의 재전송이 다른 임무를 시작하지 않는다.
- **취소**: `created`는 즉시 `canceled`; `queued`/`running`은 `cancel_requested`로 전이한 후 실행기가 취소를 확인해야 `canceled`다. 기존 `cancel_requested` 재요청은 현재 상태를 반환한다. 종결 임무에는 상태를 변경하지 않고 `409 invalid_transition`이다. `cancel_requested` 후에도 이미 완료된 결과가 확인되면 성공·실패로 끝날 수 있다. 취소 요청은 비상정지나 정지 확인이 아니다.
- 동시에 도착한 시작·취소·완료는 슬롯/임무 행 잠금과 버전 조건에 따라 직렬화하고 각 명령은 현재 상태를 재검사한다. 실행기 결과는 임무 ID와 해당 실행 세대/버전을 확인한다. 지연 결과는 최신 상태나 다른 임무를 덮어쓰지 못한다.

## API 계약 (구현 예정)

모든 응답은 JSON, 시간은 UTC, 실제 로봇 실행은 서버에서 거부한다. 기동·취소 성공 HTTP 응답은 로봇의 동작·정지 성공을 보증하지 않는다.

| 메서드·경로 | 입력 | 정상 응답 |
|---|---|---|
| `POST /api/missions` | `request_id`, `mode`, `kind`, `parameters` | 최초 `201` + 임무; 같은 요청 재전송 `200` + 기존 임무 |
| `GET /api/missions` | 선택 `before` 커서, `limit` 기본 50·최대 100 | `200` + 임무 목록·다음 커서. 안정된 정렬 키와 삭제/동시 생성 시 중복 방지 기준은 구현 시 확정·시험 |
| `GET /api/missions/{id}` | UUID | `200` + 임무 |
| `GET /api/missions/{id}/events` | 선택 `after_version`, `limit` 기본 50·최대 100 | `200` + version 오름차순 이력·다음 커서 |
| `POST /api/missions/{id}/start` | 빈 JSON 객체 | `202` + 접수 당시 상태; 이미 시작된 동일 임무 `200` + 현재 상태 |
| `POST /api/missions/{id}/cancel` | 빈 JSON 객체 | `200` + `canceled` 또는 `202` + `cancel_requested`; 이미 취소 요청 중이면 `200` + 현재 상태 |

오류는 `{"error":{"code":"...","message":"..."}}` 형식으로 비밀·DB 내부 내용을 노출하지 않는다. `400`은 JSON 구조/검증 오류(`invalid_request`, `invalid_request_id`, `unsupported_kind`, `invalid_parameters`), `403 mode_unavailable`은 실제 실행 모드 거부, `404 mission_not_found`, `409 idempotency_conflict`/`invalid_transition`/`mission_busy`, `503 database_unavailable`/`manager_unavailable`을 사용한다. HTTP 파서 오류와 경로·페이지 값 오류도 이 형식으로 통일한다. 허용하지 않은 임무를 실제 모드에서 전송하는 요청은 검증 단계에서 거부한다. 다중 사용자 인증/권한과 실제 실행 요청은 별도의 승인된 설계 전까지 노출하지 않는다.

## 실행·복구와 불확실성

- 모의 실행기는 `queued` 커밋 뒤에만 시작하고 각 단계·결과를 관리자에 보고한다. 요청 커밋 여부가 불확실할 때 클라이언트는 같은 멱등 키로 재조회/재전송하며, 외부 동작을 임의 재시도하지 않는다.
- 관리자 시작 시 DB 기반 배타 소유권을 획득한 인스턴스만 복구와 실행을 한다. 활성 소유자의 생존 확인·분리된 DB 연결·동시 관리자 기동 시 fencing 규칙을 실제 구현에서 시험하기 전 자동 복구를 활성화하지 않는다. 기존 관리자가 살아 있는 동안 다른 관리자가 그 임무를 `interrupted` 처리하면 안 된다.
- 소유권이 안전하게 확보된 재시작에 한해 이전 `queued`, `running`, `cancel_requested`를 이벤트와 함께 `interrupted`로 만들고 슬롯을 반환한다. 기존 실행기가 늦게 보낸 결과는 버전/세대 검사로 거절한다. 실기 확장 시 중단은 로봇의 정지 또는 미정지를 나타내지 않는다.
- DB 장애 시 새 실행·전이 접수를 거부한다. 이미 동작이 나간 후 결과 기록 실패는 확인 불가로 남기고 자동 재실행하지 않는다. 현재 단계에서는 외부 물리 동작이 없으며, 실제 실행의 장애 중 결과 조정·장치별 안전 처리는 별도 설계·시험 후에만 허용한다.

## 모의 시험 사례

빈 요청·잘못된 UUID·미허용 인자/모드; 같은 키 같은 요청 2회와 서로 다른 요청; 동시에 같은 키 2건; 동시에 서로 다른 임무 시작; 시작/취소/완료 경쟁; 실행기 중복·늦은 결과; 이력 삽입 실패의 롤백; 관리자 중복 기동; 실행 중 재시작; DB 연결 실패·복구를 격리 DB로 시험한다. UI는 모의 구분, 진행·실패·취소·중단과 연결 불가를 표시한다. 이 목록은 설계이며 아직 통과한 테스트가 아니다.

## 격리 시제품 구현 (2026-11-15)
`tools/ops/backend/mission_simulator.py`는 `/tmp` 아래 SQLite 파일에만 접근하며 ROS와 운영 DB에는 연결되지 않는다. 테스트 전용 시제품에서 단일 호스트의 파일 잠금으로 관리자 소유권을 확보하고 SQLite `BEGIN IMMEDIATE`로 상태·이력·단일 실행 슬롯을 트랜잭션 처리한다. 단계 진행은 현재 호출자가 명시적으로 `step()`을 호출한다. 종료된 소유자의 재시작에서는 미완료 상태를 `interrupted`로 기록한다. 버전이 맞지 않는 늦은 결과는 거부한다.

성공·실패·모의 타임아웃·취소, 동시 중복 생성·실행, 다른 관리자 진입 거부, 재시작 복구 및 이력 삽입 실패 롤백을 격리 SQLite에서 시험했다. 이는 MySQL 기반 DB 잠금·서버 통합·다중 호스트 fencing·실제 Action 검증이 아니다. MySQL 이전에는 DB 기반 소유권과 실패 조건을 별도로 구현·검증해야 하며 파일 잠금을 운영 DB의 분산 잠금으로 취급하지 않는다.

## 모의 API·화면 연결 (2026-11-15)
기존 시제품을 대시보드 프로세스의 단일 소유자로 연결하고 `/api/missions` 목록·생성·상세·이력·시작·취소 API를 추가했다. 임시 `/tmp` SQLite만 사용하며 3초 간격 모의 단계 진행이다. 목록은 최근 50건, 이력은 전체를 반환하고 페이지네이션은 아직 없다. 모의 쓰기는 `127.0.0.1:8765` 또는 `localhost:8765`와 동일한 Origin 및 JSON을 요구한다. 다중 사용자 인증이나 실제 제어 권한 체계가 아니다. 실제 모드는 거부한다. ASGI 격리 시험과 서버 렌더링만 확인했고 브라우저 조작·MySQL 기반 관리자 소유권은 미검증이다.

## 격리 검증 결과 (2026-11-15)
임시 SQLite와 격리 ASGI에서 상태·중복·실패·취소·재시작·DB 장애 복구를 포함한 관련 테스트 23건이 통과했다. 별도 localhost 시험 서버 및 Firefox에서 모의 임무 생성·시작·성공·이력·취소 흐름을 2회 확인했다. 모의·Firefox 결과는 실제 로봇, MySQL 잠금 또는 다중 호스트에 대한 근거가 아니다.
