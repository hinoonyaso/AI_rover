# 통합 캘리브레이션 관제 구현 계획

## 목적과 범위
기존 단일 센서 후보 화면을 11개 항목의 준비·측정·검증·설정 적용·복원 흐름으로 확장한다. 사용자 요청은 전체 항목의 계획과 구현 진행이다. 하드웨어를 움직이지 않는 구현 및 격리 검증을 먼저 하고, 실제 측정·구동과 실제 설정 반영은 별도로 검증한다.

## 공통 설계
1. 항목 목록에서 현재 가능한 측정과 미구현을 구분한다. 후보에는 시간, 단위, 출처, 검증 상태, 원본과 변경 범위가 필요하다.
2. 계정 권한: 조회자는 읽기, 운영자만 측정·변경 요청. 파일 경로는 서버 allowlist에서만 선택한다.
3. 후보/이력은 기존 `candidates.json`과 호환하여 원자 저장한다. 과거 기록이 없으면 없다고 표시하고 생성하지 않는다.
4. 실제 설정 적용은 계획 단계다. 사용자 지정 YAML/셸 명령을 실행하지 않는다. 항목별 형식·단위·기준 검증, 현재값 비교, 버전 충돌 감지, 백업·복원·감사·재시작 영향이 구현 및 검증된 경우에만 활성화한다. 기존 사용자는 후보 저장 후 별도 적용을 선택했다.
5. 브라우저와 CLI/ROS에서 공유할 수 있는 순수 계산 모듈과 명시적 입력 계약을 사용한다. 대시보드·API는 물리 명령을 직접 생성하지 않는다.
6. 실제 바퀴·팔·그리퍼 구동과 토크 변경은 프로젝트 안전 규칙에 따른 별도 승인과 준비가 필요하다. 시뮬레이션 성공은 실기 성공이 아니다.

## 단계
1. 공통 항목 목록·진행 상태와 기존 후보 이력(기존 파일 호환) 구현.
2. IMU·컬러 카메라의 측정 품질, 원본 데이터, 현재값 비교 및 독립 검증을 보완한다.
3. 입력만으로 검증할 수 있는 footprint·배터리·LiDAR 관찰 결과 수집 및 단위 검증을 구현한다.
4. 오도메트리·휠의 격리 기록/계산과 Gazebo 검증을 구현한다.
5. 관절·그리퍼·TCP의 비구동 후보와 시뮬레이션 검증을 구현한다.
6. 각 항목별 적용·복원 어댑터는 실제 설정의 소비 경로와 복구 조건을 입증한 뒤, 별도 승인 및 안전 게이트 아래 연결한다.

## 주요 한계
후보는 곧바로 운용 가능한 값이 아니다. 센서·기기·단위·좌표·측정 품질·보정 전후 독립 기준 없이 성공을 선언하지 않는다. 실제 로봇 운전과 임의 구성 덮어쓰기를 하지 않는다.

## 2026-11-17 진행
11종 목록, 기존 후보와 호환되는 새 후보 이력, base_footprint 기준 네 방향 실측의 사각형 미적용 후보를 구현했다. 사용자 입력이 안전 여유를 포함하는지는 미확인으로 표시한다. 기존 설정과 이력을 만들어 덮어쓰지 않으며, 배터리의 최신 표본과 외부 전압계 단일 비교 저장도 추가했다. 다른 7개 항목의 측정 및 설정 적용·복원은 미구현이다.

## LiDAR 위치 후보 구현
base_link 기준 lidar_link 원점의 X/Y/Z 수동 실측을 cm로 받아 m로 저장한다. 양의 X/Y/Z는 각각 앞/왼쪽/위다. 실제 TF 조회나 현재 설정과의 자동 비교는 하지 않으며, 프레임 원점은 사용자가 확인해야 한다. `lidar_frame`은 `lidar_link`와 별도 회전 관계가 있으므로 이 기록만으로 방향 또는 스캔 정합이 검증된 것은 아니다. 활성 URDF/TF는 변경하지 않는다.

## 오도메트리 단일 시험 비교
이미 수행한 동일 시험의 실측값과 기록값을 수동으로 입력한다. 직진/횡이동은 cm, 회전은 누적 각도(deg)를 쓰고 전진/왼쪽/반시계가 양수다. 오차는 기록 − 실측이며 백분율은 실측 절댓값을 분모로 한다. 명령 적분·엔코더·EKF 출처를 구분한다. 0에 가까운 기준은 거부한다. 운행, ROS 기록 자동 수집, 보정 계수 계산과 적용은 지원하지 않는다. 명령 기반 scale의 소비 경로가 엔코더 및 EKF와 다르므로 단일 비교만으로 scale을 제안하지 않는다.

## 휠 전진 시험 관찰 기록
기존 전진 시험에 대한 각 바퀴의 지면 기준 앞/뒤 회전, 정지 또는 미확인을 수동 기록한다. 시뮬레이션과 실기를 구별하고 자동 성공 판정·속도 측정·구동·설정 변경은 하지 않는다. 실제 관찰 또는 실행 전 안전 준비와 별도 승인이 필요하다. 저장 시간은 관찰 시점이 아니라 기록 저장 시간이다.

## 컬러·깊이 CameraInfo 표시
ROS 모니터는 각 `/depth_cam/{color,depth}/camera_info`를 별도로 구독해 최신 유효 내부 파라미터와 수신 시각을 저장한다. 대시보드는 오래된 스냅샷·관측을 숨긴다. 드라이버 관측값은 공장 보정 여부·정확도·RGB-depth 정합 증거가 아니며 자동 비교나 적용은 지원하지 않는다. ROS 모니터 및 대시보드 재시작 후 사용 가능하다.

## 카메라 후보와 현재값 비교
동일 해상도일 때 컬러 CameraInfo와 JPEG 후보의 fx/fy/cx/cy 차이를 픽셀 단위로 표시한다. 카메라 장치 동일성은 자동 검증할 수 없고 왜곡 모델 차이로 왜곡 계수는 비교하지 않는다. 차이나 재투영 RMS만으로 보정 정확도·합격 여부를 판단하지 않는다.

## RGB·깊이 수동 대응점 비교
최신 컬러·깊이 CameraInfo의 해상도와 프레임 일치가 확인되면 수동 대응점 3~10개에 대한 픽셀 거리와 RMS를 저장한다. 실제 장치에서 두 CameraInfo는 640×360, depth_cam_color_optical_frame으로 확인했으며, 실제 메타데이터와 합성 점으로 API 계산을 검증했다. 이미지 동기화, 대응점 정확도 및 보정 성공은 확인하지 않는다.

## 팔·그리퍼 관절 비교
ROS 모니터는 실행 중 base_node의 관절 이름·서보 ID 파라미터를 읽고 /joint_states와 /arm/servo_stats의 실제 응답 나이를 사용한다. 관측과 서보 응답이 최신일 때만 외부 기준 각도와 비교해 저장하며 설정을 바꾸지 않는다. 대응표는 15초, 진단 스냅샷은 3초, 실제 서보 응답은 1.5초 제한이다. 출처 혼재·기준 각도·실제 물리 위치의 정확성은 독립 검증이 필요하다. 그리퍼 폭과 파지, TCP 및 설정 적용은 제공하지 않는다. 현재 base_node는 sensor_only로 팔 발행이 꺼져 있다.

## 카메라 고정 자세 대응점 강체 변환 및 자이로 설정
카메라 광학 프레임과 base_link 또는 gripper_link의 동일한 4~30점으로 Kabsch 강체 변환과 잔차를 계산한다. 입력 점은 같은 자세여야 하며 여러 자세의 핸드아이·TCP 보정은 아니다. 자이로 후보는 설치된 base.yaml의 기존 bias가 측정 당시 값과 같고 확인한 후보 및 파일 해시가 유지될 때만 운영자 명시 요청으로 적용한다. 적용 전 전체 파일을 사용자 전용 디렉터리에 백업하고 변경되지 않은 적용 결과에 한해 복원한다. 노드는 자동 재시작하지 않는다. 원본 src YAML은 변경하지 않아 재빌드 시 설치 설정이 덮일 수 있다.

## 다중 자세 핸드아이 후보
base_T_link4와 camera_T_target 4×4 자세 쌍 5~30개로 OpenCV Park 핸드아이를 계산한다. 카메라는 link4에 고정되고 표적은 움직이지 않아야 하며, 분리된 회전 방향과 유효한 강체 행렬이 필요하다. 고정 표적 일관성 잔차를 제공하지만 입력 자세의 동기·실제 물리적 정확성과 독립 검증을 보장하지 않는다. 자세는 수동 JSON 입력이고 실제 구동이나 TF 변경은 하지 않는다. TCP 보정과 구분한다.

## 2026-11-17 후속 구현 현황

현재 각 항목의 세부 기능 및 제약은 `tools/ops/README.md`의 센서 보정 후보 절을 기준으로 한다. 앞의 단계별 기록은 당시 상태다. 추가된 기능에는 배터리·그리퍼 표시 보정, 기본 Nav2 외형, 카메라 정보·IMU·관절·오도메트리·LiDAR 위치/독립 실측 장착 yaw·TCP/핸드아이의 별도 검토·백업·적용·복원이 포함된다. 실측 장착 yaw는 스캔 오차를 자동 변환하지 않고 lidar_frame의 별도 회전을 보존한다. 팔 관측 서비스는 위치·온도 읽기만 하며 별도 센서 모드와 동시에 실행하지 않는다.

실제 로봇의 읽기 전용 팔 관측에서 6개 관절을 확인하고 TCP TF 자세를 3회 수집했다. 실제 다중 자세 보정, 구동 및 실제 설정 변경은 하지 않았다. 휠 펌웨어 속도 보정, 그리퍼 파지력 보정, RGB-depth 장치 내부 정합 보정과 실기 정확도 확인은 남아 있으므로 전체 항목의 물리 보정 완료로 취급하지 않는다.

## 남은 세 항목 연동 방향

- RGB-D: 실행 중 드라이버는 정합 모드 변경 서비스를 제공하지만 공장 내부 파라미터 쓰기/읽기 복원 계약은 확인되지 않았다. 검토 가능한 설치 설정의 정합 모드(HW_D2C/SW_D2C/OFF)만 백업·적용·복원하고 카메라를 별도 재시작해 반영한다. 모드 변경은 카메라-깊이 외부 파라미터 보정으로 표시하지 않는다. SW_C2D는 현재 다운스트림이 깊이를 컬러 프레임으로 사용하는 계약과 달라 제외한다.
- 휠: 제어기 PID 변경 명령은 휘발성이고 설정 읽기·복구 확인 경로가 없다. 외부 속도계와 여러 속도의 피드백을 비교해 편차와 회귀 후보를 산출한다. 이 값으로 PID를 추정하거나 제어기에 적용하지 않는다.
- 그리퍼: 서보는 힘/전류를 반환하지 않는다. 외부 힘 계측기의 수동 측정과 접촉 프로파일을 연계하되 물체별 시험값으로만 기록하고, 힘을 센서 측정이나 안전 제한으로 해석하지 않는다. 실제 파지 구동은 별도 승인이다.

## 사용자 범위 조정
그리퍼 외부 힘 기록은 UI/API에서 제외하고 기존 파일의 이력은 삭제하지 않는다. MCU PID는 실행 중 쓰기만 확인되며 읽기·복원 경로가 없으므로 대시보드 자동 적용 범위에서 제외한다. 체커보드 영상 및 타임스탬프 TF로 핸드아이 자세를 수집하며, RGB-D 3D 대응점으로 외부 변환 후보를 계산한다. 장치 공장 설정에 후보를 쓰는 경로는 확인되지 않았다.

## RGB-D 외부 변환 소프트웨어 처리
원본 depth 광학 좌표와 color 광학 좌표의 별도 CameraInfo와 미정합 16UC1 영상을 입력으로 하여 후보 강체 변환을 적용하고 `/depth_cam/depth_corrected/image_raw`에 발행한다. 깊이 투영 충돌은 가장 가까운 z값을 선택하고 빈 픽셀은 0이다. 현재의 안전·인식 토픽에는 자동 연결하지 않는다. 후보는 해시·백업·복원을 지원하며 장치 공장값은 수정하지 않는다. 격리 ROS에서 합성 데이터로 노드 출력을 확인했고 실기 정합과 성능은 미검증이다.

## 보정 깊이의 인식 연결
큐브 인식은 `cube_detector.launch.py depth_source:=corrected`에서 보정 토픽을 명시적으로 구독한다. 장애물 포인트클라우드는 `camera.launch.py depth_source:=corrected corrected_background_path:=...`에서만 전환하며 기본값은 기존 입력이다. 보정 배경 파일과 활성 변환의 해시가 일치해야 런치가 시작되고, 실행 중 활성 변환이 바뀌거나 사라지면 장애물·지우기 클라우드를 발행하지 않는다. 같은 크기의 기준 영상이더라도 실제 배경·팔 홈 자세·카메라 내부 파라미터·설치 위치가 적합한지는 해시만으로 보증되지 않으며 별도 확인해야 한다. 입력 미수신 시 자동으로 원본으로 대체하지 않는다. 실기 안전 검증 전이다.
