# PRD: 임무 생성·실행·관제

신뢰 수준: 사용자 승인 계획(2026-11-15). 사용자는 임무 생성부터 실행까지 전체 기능을 요청했다. 기존 읽기 전용 대시보드 범위를 확장하는 계획이며 실제 로봇 구동 승인이나 실기 시험 완료를 뜻하지 않는다.

## 목표
운영자가 임무를 생성하고 실행 상태·현재 단계·결과를 추적할 수 있게 한다. 우선 로봇 없이 모의 임무의 전체 흐름을 검증하고, 이후 기존 ROS2 기능을 연결해 실제 임무까지 확장한다. 상태는 실제 실행 결과에서만 결정하며 주행 결과를 전체 임무 성공으로 대체하지 않는다.

## 현재 상태와 근거
- `tools/ops/`에는 localhost 전용 읽기 대시보드와 MySQL이 있으나 임무 관리자, 임무 상태 인터페이스와 이력 스키마는 없다. `robot_events`는 현재 주로 서버 기동을 기록한다.
- `checklist/PROJECT_CHECKLIST.md` 17절의 Mission Manager와 BT는 미구현이다. Nav2 `NavigateToPose`, 접촉 파지 `Grasp.action` 등은 개별 기능이며 전체 임무의 소유자가 아니다.
- 기존 승인된 `prd/dashboard-monitoring.md`는 로봇 제어와 임무 실행을 범위 밖에 둔다. 이 PRD는 사용자의 새 요청에 따라 그 제한을 **임무 기능에 한해** 변경하는 제안이다. 읽기 전용 대시보드가 안전 기능이라는 뜻은 아니다.
- `docs/PLAN_ARM_TO_MVP.md`는 Stack Light 점검과 부품 Pick & Place를 포함한 Mission BT를 계획한다. 점검·조작 전체에 필요한 Action과 조건이 이미 준비됐다고 가정하지 않는다.

## 범위
- 정해진 임무 종류와 인자를 검증해 임무 ID를 발급하고 생성·시작·취소 요청을 처리한다. 초기에는 동시 실행 하나만 허용하고 중복 요청을 식별한다.
- 상태(`created`, `queued`, `running`, `cancel_requested`, `succeeded`, `failed`, `canceled`, `interrupted`)와 단계, 진행 시각, 오류·취소 사유, 결과, 실행 모드(`simulation`/`robot`)를 일관되게 보관·표시한다. 미확인/연결 끊김은 실행 결과와 별개로 표시한다.
- 관제 화면에서 임무 생성, 실행·취소, 현재 단계, 이력과 결과를 확인한다. 모의와 실제를 항상 구분한다.
- 초기 구현은 로봇 장치나 ROS 제어에 연결되지 않는 모의 실행기로 성공·실패·타임아웃·취소·재시작을 검증한다. 장기 목표는 동일 계약의 실제 실행 어댑터를 통해 ROS2 Action과 BehaviorTree.CPP 기반 Mission Manager에 연결하는 것이다.
- 실제 어댑터는 점검·주행·조작 등 각 동작의 준비 조건과 결과를 확인하고, 필요한 개별 Action이 없으면 실패 또는 사용 불가를 표시한다. 없는 Action을 성공으로 처리하지 않는다.
- 임무와 전이 이력을 DB에 기록한다. 각 상태 변경과 그 이력 기록은 같은 트랜잭션으로 처리하고 DB 장애 시 실행 요청을 거부한다. 실행 중 재시작 시 기존 임무를 자동 재개하지 않고 `interrupted`로 복구한다(실기 동작 중일 가능성과 정지 여부는 별도 확인).

## 구조와 경계
`React → localhost FastAPI → 검증된 명령 → Mission Manager → 실행 어댑터(모의 / 실제 BT·ROS Action) → 상태 이벤트 → DB / API → React`.

- 임무 상태와 활성 임무의 단일 소유자는 Mission Manager다. 상태 조회는 API, 실행은 제어 명령 인터페이스로 분리한다. 기존 센서 모니터는 읽기 전용을 유지한다.
- 초기 개발은 MySQL과 기존 UI를 재사용한다. BehaviorTree.CPP/ROS Action은 실제 단계에서 도입하고 임시 모의 실행을 실제 임무 관리자처럼 표시하지 않는다. 웹 서버가 직접 PWM·시리얼·`cmd_vel`을 발행하지 않는다.
- 대안: Nav2 상태만 표시하면 구현은 작지만 임무 전체 결과를 표현하지 못한다. 웹 프로세스가 직접 로봇을 제어하면 중복 실행과 상태 소유권이 불명확해져 선택하지 않는다.
- 실기 명령을 노출하기 전에 사용자 인증·권한, 명령 출처, 재생/중복 방지, 세션 만료 및 취소·연결 단절 정책을 별도 설계·검증한다. 현 인증 없는 localhost/SSH 환경만으로 원격 제어가 안전하다고 간주하지 않는다.

## 상태 및 실패 규칙
- 허용 전이와 종결 상태는 구현 전 확정한다. `cancel_requested`는 취소 요청 접수일 뿐 정지 성공이 아니며, 실제 실행기가 취소 결과를 보고하기 전 `canceled`로 표시하지 않는다. 타임아웃·취소 미확인은 실패/중단과 실제 장치 상태 미확인을 구분한다.
- 실행 요청의 동시성 제어는 DB 수준의 원자적 상태 변경 및 단일 실행 소유권으로 강제한다. 외부 실행 전 영속화 실패 시 전송하지 않는다. 이미 보낸 동작의 결과 기록에 실패하면 성공이나 정지를 추측하지 않고 불확실 상태로 표시하며 자동 재시도하지 않는다.
- 통신 단절, 작업자 브라우저 종료, 관리자 재시작, Action 중복·늦은 응답, 취소 경쟁, DB 오류·복구, 실패 후 복구는 각각 별도 시험한다. 무조건 복귀·재시도·그리퍼 해제를 하지 않는다. 물체를 잡고 있는 그리퍼의 HOLDING 및 Release 소유권은 기존 파지 계약을 보존한다.
- 비상정지는 독립적인 실제 안전 경로여야 한다. 웹의 취소 버튼은 비상정지가 아니다.

## 데이터 및 인터페이스 초안
- 임무: 고유 ID, 요청 중복 방지 키, 종류·검증된 인자, 실행 모드, 상태, 현재 단계, 생성/시작/종료 시각(UTC), 결과·오류 사유, 상태 버전.
- 이력: 임무 ID, 순서 번호, 이전/다음 상태, 단계, 시각(UTC), 출처, 사유. 단조 증가 버전으로 늦은 이벤트를 무시하며 이력은 임무와 구분한다.
- 위치 인자는 승인된 semantic map의 이름과 `map` 프레임 좌표(m, rad)를 사용한다. 임의 좌표를 유효한 위치로 간주하지 않는다. 샘플 좌표·단계 제한시간·배터리 기준은 가정해 확정하지 않고 실제 연동 전에 정한다.
- 읽기: 목록·상세·상태·이력 API. 쓰기: 생성·실행·취소 API. 초기는 모의 실행 명령만 허용하며 실제 실행은 기능 게이트와 별도 권한 검증이 준비되기 전까지 거부한다. 경로·ROS 메시지·QoS·Action 서버의 정확한 계약은 연결 전 정의하고 시험한다.

## 비범위 및 제약
- MVP 이후 Gauge/OCR/Valve 확장, RAG, 임의 LLM 제어, 공개 인터넷 노출은 이번 초기 구현에서 제외한다.
- 최초 실제 임무 대상 및 검증 가능한 Action은 개발 시점에 사용자와 확정한다. `CheckReady` 세부 판정, 취소 타임아웃, 중단 시 장치별 처리와 작업 공간·배터리 조건은 실제 동작 전에 정한다.
- 기존 맵·보정치와 운영 DB 데이터를 덮어쓰지 않는다. 스키마는 기존 테이블과 호환되는 비파괴 migration 및 백업·복구 절차를 마련한다.
- 모터·팔 구동 및 팔 토크 변경은 매번 사용자 승인 후 프로젝트의 L2~L5 안전 규칙에 따른다. L1 시뮬레이션/모의 결과는 실기 성공의 근거가 아니다.

## 구현 순서 제안
1. 임무 종류·상태 전이·실행 모드·실패 처리와 API/ROS 계약을 구체화하고 시험 데이터/실기 게이트를 정한다.
2. 모의 실행 기반의 임무 관리자, 트랜잭션 이력 및 재시작 복구를 구현한다.
3. 대시보드에서 모의 임무 생성·실행·취소·현재 단계·이력을 연결한다.
4. 격리 환경에서 경쟁 조건·오류·재시작·취소를 검증하고 운영 문서를 작성한다.
5. 실제 사용할 임무 하나와 Action 준비 상태를 확인한 뒤 BT/ROS 어댑터와 권한·실행 게이트를 구현하고 시뮬레이션한다.
6. 별도 승인과 안전 준비 후 단계별 실기 시험, 전체 임무 통합 검증을 수행한다.

## 완료 기준
- 모의 실행에서 생성→진행→결과, 단계·이력 표시, 실패·타임아웃·취소, 중복 요청과 재시작 복구가 시험 계획을 통과한다. 모의 실행에서 로봇 제어 명령은 발생하지 않는다.
- 실제 실행은 필요한 Action·권한·안전 준비가 확인되기 전 거부된다. 실제 결과를 얻지 못한 경우 성공·정지로 표시하지 않는다.
- 실제 임무는 사용자와 확정한 시나리오, 안전 게이트 및 실기 기준을 충족해야 전체 완료다. `docs/PLAN_ARM_TO_MVP.md`의 10회 중 8회 이상은 전체 임무 게이트이며 지금 미검증이다. 하드웨어 없는 구현 완료와 실기 완료는 따로 기록한다.

## 모의 상태 계약 1차 구현 (2026-11-15)
`tools/ops/backend/mission_contract.py`는 외부 접근 없이 상태 전이와 요청을 검증하는 독립 로직이다. `created → queued → running → succeeded/failed`가 기본 경로이며, 실행 중 취소는 `cancel_requested`를 거쳐 실행기의 확인된 결과(`canceled`, `succeeded`, `failed`) 또는 관리자 중단(`interrupted`)으로 종결한다. 생성 직후 임무는 실행기 없이 `canceled`로 전환할 수 있다. `interrupted`를 포함한 종결 상태는 변경되지 않는다. 큐 또는 실행 중 재시작은 `interrupted`로 표시한다.

현재 입력 계약은 UUID 문자열 `request_id`, `mode: simulation`, `kind: inspection_demo`, 빈 객체 `parameters`만 받는다. `inspection_demo`는 로봇 연결 없는 모의 임무 이름이며 실제 점검 수행을 의미하지 않는다. `robot` 모드는 `mode_unavailable`로 거부한다. DB 중복 요청의 원자적 처리, 실제 API·ROS 계약, 모의 실행 및 실기 게이트는 미구현이며 이후 작업이다. 로직은 아직 서버나 UI에 연결하지 않았다.

## 저장·API 상세 설계
중복 요청, 상태·이력 스키마, 단일 실행 슬롯, API 및 복구 규칙은 `prd/mission-management-contract.md`를 따른다. 구현 전 설계이며 실제 API·DB 기능은 아직 없다.

## 주행 단계 가짜 Action 시험 (2026-11-15)
전체 임무의 첫 연동 후보는 Nav2 목표 지점 이동이다. 실제 임무 목적지와 작업 시나리오는 아직 확정하지 않았다. `tools/mission/`에는 실제 `/navigate_to_pose` 연결이 불가능한 격리 테스트 전용 어댑터와 가짜 서버가 있다. 성공·거부·실패·취소 확인·취소 미확인·서버 부재를 시험했다. 이는 전체 임무 성공, 실제 로봇 실행 권한, Gazebo에서의 이동이나 물리적 안전의 증거가 아니다. 나머지 실제 BT/ROS 연동 및 시뮬레이터 검증은 남아 있다.
