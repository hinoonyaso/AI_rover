# 시험 계획 초안: Gazebo 경광등 점검

상태: PRD와 함께 승인(2026-11-16). 실기 주행·팔 동작은 범위 밖이다.

1. **판정 로직 L0**: 색상별 점등·소등·깜빡임과 여러 색 조합의 재현 가능한 영상으로 기대 결과를 비교한다. 빈 영상, 오래된 프레임, 부족한 표본, 대상 가림, 잘못된 영역은 `unknown` 또는 명시적 오류여야 한다.
2. **Gazebo 영상 시험**: 격리 월드에서 가상 카메라의 실제 영상으로 색상별 상태를 확인하고 카메라 시점·영역·표본 시간·재현 명령을 기록한다. 인위적으로 만든 배열만으로 통과 처리하지 않는다.
3. **임무 통합 L0 및 Gazebo**: 주행 성공 뒤 판정 결과가 저장·조회·표시되는지 확인한다. 주행 실패, 영상 부재, 점검 실패, 취소·취소 미확인, 실행 중 재시작에서 거짓 성공이 없어야 한다.
4. **실기 성능**: 이 시험의 완료 기준에 포함하지 않는다. 실기 조명·거리·깜빡임을 포함한 `docs/PLAN_ARM_TO_MVP.md`의 50회 이상 시험은 별도 준비와 승인 후 실시한다.

구체적인 표본 수, 시간 간격 및 상태 판정 경계는 시험 월드의 렌더링·프레임 속도를 확인한 뒤 기록하고, 그 경계를 포함하는 테스트를 작성한다.

## 1차 합성 영상 결과 (2026-11-16)
`test_stack_light.py` 4건 통과. 첫 시제품은 5프레임 이상, 관측 길이 2초 이상, 프레임 간격 및 마지막 영상의 경과 시간 각각 최대 0.6초를 요구한다. 각 영역에서 해당 색이 절반 이상 보여야 하며 HSV 밝기 65 이하를 소등, 160 이상을 점등으로 분류한다. 최소 2회 상태 전환을 깜빡임으로 보고 1회 전환은 미확인이다. 이 값은 합성 영상용 초기값으로 Gazebo 카메라에서 아직 확인하거나 보정하지 않았다.

## 독립 Gazebo 카메라 결과 (2026-11-16)
`tools/mission/stack_light_fixture.sdf`의 고정 RGB 카메라에서 `ros_gz_bridge`를 거쳐 7프레임, 약 3.03초의 영상을 수신했다. `tools/mission/check_stack_fixture.py` 결과는 빨강 `on`, 노랑 `off`, 초록 `on`으로 월드의 설정과 일치했다. 각 중앙 픽셀 RGB는 각각 `[255,0,0]`, `[47,47,0]`, `[0,255,0]`이었다. 격리 ROS 도메인 31, localhost discovery, 별도 Gazebo partition을 사용했다. 카메라는 고정되어 있으며 로봇이나 Nav2는 실행하지 않았다.

추가 시험에서는 Gazebo 서비스로 초록색의 밝은 가상 렌즈를 이동시켜 어두운 렌즈를 드러냈다. 초록 소등은 7프레임 약 3.03초에서 `off`, 렌즈를 약 0.8초 간격으로 반복 전환한 영상은 11프레임 약 5.01초에서 `blinking`으로 판정됐다. 전환은 카메라에 보이는 가상 물체만 대상으로 하며 로봇 명령이 아니다.

추가로 `make_stack_fixture_variant.py`로 `/tmp`에 반전 월드를 만들고 빨강 `off`, 노랑 `on`, 초록 `on`을 7프레임 약 3.01초 동안 확인했다. 중앙 RGB는 각각 `[47,0,0]`, `[255,255,0]`, `[0,255,0]`이었다. 세 색의 점등·소등은 각각 확인했지만 빨강·노랑의 깜빡임, 가림과 조명 변화는 아직 확인하지 않았다.

별도로 로봇 Gazebo를 주행 목표 위치에 정지 상태로 생성하여 `base_footprint → depth_cam_link` TF를 확인했다. 카메라는 로봇 기준 높이 약 0.351 m, pitch 약 +0.880 rad(50.4°)이며 Gazebo 카메라의 +x 시선은 아래를 향한다. 즉 기존 홈 자세에서 수직으로 세운 높은 경광등을 볼 수 있다고 가정할 수 없다. 이 시험은 팔이나 바퀴를 구동하지 않았다.

같은 목표 위치에서 정지한 로봇의 `/depth_cam/color/image_raw`와 `stack_light_robot_view.sdf`의 기울어진 가상 시험 대상을 사용해 빨강 `on`, 노랑 `off`, 초록 `on`을 판정했다. 9프레임의 관측 길이는 약 3.06초였고 프레임 간격은 0.324~0.474초였다. 처음에는 spawn 도구가 SDF의 모델 pose를 원점으로 덮어써 대상이 보이지 않았고, Gazebo 위치 서비스를 이용해 지정된 위치로 옮긴 뒤 성공했다. 한 번의 시험에서는 프레임 간격 0.608초가 판정 제한을 넘어 `unknown`이 나왔으며, 시험 도구는 긴 간격 이후 새 관측 창을 모은다. 이는 정지 상태의 한 배치·한 조합이며 주행 후 위치 오차, 다른 색 조합 및 깜빡임 검증은 아니다. 가상 대상은 카메라를 향해 기울여 놓은 비충돌 영상 시험판이며 실제 설비 배치를 뜻하지 않는다.

재현: 앞서 명시한 격리 환경에서 `ros2 launch jetrover_gazebo sim.launch.py gui:=false x:=1.0 y:=1.45 yaw:=1.5707963`를 기동한다. `ros2 run ros_gz_sim create -world jetrover_room -file tools/mission/stack_light_robot_view.sdf -name robot_view_stack_light`로 추가한 후 `gz service -s /world/jetrover_room/set_pose --reqtype gz.msgs.Pose --reptype gz.msgs.Boolean --timeout 5000 --req 'name: "robot_view_stack_light", position: {x: 1.001, y: 1.770, z: 0.158}, orientation: {x: -0.301, y: 0.301, z: 0.640, w: 0.640}'`로 위치를 설정한다. `/usr/bin/python3 tools/mission/check_stack_robot_view.py`로 영상과 결과를 확인하고 Gazebo를 종료한다.

재현 시 각 터미널에서 `ROS_DOMAIN_ID=31`, `ROS_AUTOMATIC_DISCOVERY_RANGE=LOCALHOST`, `RMW_IMPLEMENTATION=rmw_fastrtps_cpp`, `GZ_IP=127.0.0.1`, 동일한 전용 `GZ_PARTITION`을 설정하고 다른 ROS discovery 설정을 해제한다. `gz sim -s -r tools/mission/stack_light_fixture.sdf`와 `ros2 run ros_gz_bridge parameter_bridge '/stack_test/image@sensor_msgs/msg/Image[gz.msgs.Image'`를 실행한 뒤 `/usr/bin/python3 tools/mission/check_stack_fixture.py`를 실행한다. 시험 종료 후 두 프로세스를 중지한다.

## 브라우저 통합·점검 취소 (2026-11-16)
`test_dashboard_gazebo.py --inspection-browser`로 격리 Firefox에서 임무를 생성·실행하고 독립 Gazebo 주행 후 카메라 결과 표시를 확인했다. 이력은 생성→대기→주행→점검→성공이고 빨강 on·노랑 off·초록 on(5프레임, 약 2.15초)을 표시했다. 이전 API 시험을 포함해 위치 탐색·CPU 사용 개선 후 각각 새 Gazebo에서 성공 2회다.

`--inspection-cancel` 시험은 가상 대상이 없는 월드에서 주행 후 점검 단계에 들어간 것을 확인하고 Firefox의 취소 버튼을 눌렀다. 이력은 생성→대기→주행→점검→취소 요청→취소 확인이며 결과는 비어 있다. 임시 SQLite 이력 기록 실패 후 재시도, 단계 전환과 취소의 경쟁은 단위 시험으로 확인했다. 대시보드 회귀 시험 34건, 별도 Firefox 단계·결과 화면 시험 통과. 실행 중 관리자 재시작과 영상 단절의 Gazebo 통합, 다른 색 조합 및 장시간 반복은 미검증이다.

추가로 카메라 발행자가 없는 별도 localhost ROS 도메인에서 관측기가 제한시간 후 `unavailable`, 즉시 취소 요청에 `canceled`를 반환하는 것을 확인했다. 이것은 관측기 단독 시험이며 주행 중 영상 단절의 Gazebo 통합 시험을 대체하지 않는다.

## 재시작·영상 중단·반복 및 반전 색상 (2026-11-16)
- `test_dashboard_gazebo.py --inspection-restart`: Gazebo 주행 후 점검 단계에서 격리 관리자 서버를 재시작했다. 기존 임무는 자동 재개되지 않고 `interrupted`, 사유 `manager_restarted`, 결과 없음으로 복구됐다. 이력은 생성→대기→주행→점검→중단이다.
- `test_observer_disconnect_ros.py`: 별도 localhost ROS 도메인에서 실제 구독자가 RGB 영상 4프레임을 받은 뒤 발행을 중단했고, 충분한 표본을 얻지 못해 `unavailable`을 반환했다. Gazebo 주행 중 브리지 중단 시험은 아니다.
- `--inspection-repeat`: 매 회차 Gazebo를 새로 시작해 주행·점검하는 시험에서 1·2회차는 on/off/on을 확인해 성공했다. 3회차는 임무 생성 전 Nav2의 `Managed nodes are active` 기동 대기 90초가 초과되어 시험 전체가 실패했다. 당시 AMCL 상태 전환 응답 시간 초과 경고와 map TF 대기 로그가 있었으며 원인은 확정하지 못했다. 3회 연속 성공으로 기록하지 않는다.
- `--inspection-inverted`: 별도 Gazebo에서 빨강 off·노랑 on·초록 off를 설정하고 주행 후 카메라·임무 결과에서 일치함을 1회 확인했다. RGB 판정 관련 단위 시험 8건과 관제 서버 회귀 시험 34건 통과.

당시 남은 과제는 Nav2 반복 기동 시간 초과 원인 확인, 장시간 반복, 주행 또는 점검 중 Gazebo 영상 브리지 중단, 로봇 카메라의 깜빡임 조합 및 실기 검증이었다. 후속 시험은 아래 기록을 따른다. Gazebo 결과는 실물 설비 성능을 의미하지 않는다.

## Nav2 기동 진단 (2026-11-16)
이전 3회 반복 중 세 번째 Nav2 기동에서 지도 TF 대기와 AMCL 상태 전환 응답 시간 초과가 관찰됐다. 원인 후보로 이전 ROS 노드 중복과 일시적인 기동 경쟁을 구분하기 위해 `diagnose_nav2_restarts.py`로 주행 목표를 보내지 않고 Gazebo와 Nav2를 각각 세 번 새로 시작했다. 세 회차에서 위치 추정 관리자는 준비됐고 각 시험 전후 독립 ROS 노드 목록에서 잔여 노드를 발견하지 못했다. **정정**: 당시 시험 도구가 두 관리자의 같은 완료 문구를 구분하지 못했으므로 주행 관리자까지 3회 준비됐다는 이전 기록은 근거가 없다. 로그·노드 목록은 `/tmp/jetinspect-nav2-startup-dna8hs2n`에 보존했다(임시 파일이므로 정리·재부팅 시 삭제 가능).

이 진단은 주행과 임무 실행을 포함하지 않아 이전 실패와 완전히 같은 조건은 아니다. 기존 실패의 원인은 확정되지 않았고 코드 설정을 임의로 변경하지 않았다. 시험 도구는 이제 시뮬레이션 임무가 초기 위치를 설정할 기회를 먼저 제공한 뒤 위치 추정과 주행 관리자의 완료 메시지를 모두 확인한다.

### Fast DDS 전송 비교: 예비 결과
주행 명령 없이 가상 하드웨어를 확인하고 AMCL 초기 위치를 설정한 뒤 두 라이프사이클 관리자의 활성화를 확인하는 진단을 6회 실행했다. 기본 전송 설정에서는 5회가 준비됐고, 6회차에서 AMCL의 `/amcl/change_state` 응답 전송 시간 초과가 재현됐다. 당시 AMCL 프로세스는 살아 있었지만 데몬을 사용하지 않은 ROS 노드 목록에는 나타나지 않았다. 증거: `/tmp/jetinspect-nav2-startup-0pfk49u4`.

같은 격리 조건에서 진단 프로세스에 `FASTDDS_BUILTIN_TRANSPORTS=UDPv4`를 설정한 시험은 6회 모두 Nav2 준비를 확인했다. 증거: `/tmp/jetinspect-nav2-startup-ulpvam2q`. **정정:** 별도 노드의 `/proc/<pid>/maps`를 확인한 결과 이 환경 변수와 localhost discovery를 함께 사용해도 Fast DDS 공유 메모리가 매핑됐다. 따라서 이 6회는 공유 메모리를 배제한 대조 시험이 아니며, 두 결과만으로 공유 메모리가 근본 원인이라거나 UDP 설정이 장애를 해결한다고 결론 내릴 수 없다. 운영 환경에는 해당 설정을 적용하지 않았다.

### 격리 UDP 프로필 대조 검증 (2026-11-16)
ROS 도메인 98에서 매회 Gazebo와 Nav2를 새로 기동하고 두 설정을 교대로 각각 6회 시험했다. 기본 설정은 `LOCALHOST` 탐색이며, 비교 설정은 `SUBNET` 탐색과 루프백 주소만 허용하고 내장 전송을 끈 UDPv4 XML 프로필을 사용했다. 가상 하드웨어와 Gazebo 위치를 확인한 후 초기 위치를 설정하고 두 Nav2 라이프사이클 관리자의 활성화를 기다렸다. 주행 목표는 보내지 않았다.

| 설정 | 준비 성공 | 관측 |
|---|---:|---|
| 기본 설정 | 0/6 | 3회는 위치 추정 활성화 시간 초과, 3회는 초기 위치 설정 도구 75초 시간 초과. 두 Nav2 프로세스 모두 공유 메모리 매핑 확인. 5회차 map_server에서 `/map_server/change_state` 응답 전송 시간 초과 확인. |
| UDP 프로필 | 6/6 | AMCL과 smoother_server 모두 매회 Fast DDS 공유 메모리 매핑 없음. 초기 위치와 두 관리자의 활성화 확인. |

별도 두 노드 간 메시지 송수신도 공유 메모리 매핑 없이 확인했다. 이는 해당 시험 환경에서 UDP 프로필이 유력한 **우회 후보**임을 보여주지만, 탐색 설정도 함께 바뀌었으므로 공유 메모리 자체가 근본 원인이라는 인과관계는 미확정이다. 전체 임무·장시간·실기 검증이 아니며, 기존 시뮬레이션 실행기의 localhost 격리 검증을 우회하거나 운영 설정을 변경하지 않았다. Fast DDS `2.14.6`, rmw_fastrtps_cpp `8.4.4`, Navigation2 `1.3.13`; 결과와 프로필은 `docs/benchmarks/sim/dds-startup-20261116/`, 개별 원본 로그는 임시 경로 `/tmp/jetinspect-dds-compare-q5_c__70/`에 있다.

### 공유 메모리 단일 변수 재검증과 시뮬레이션 우회
이후 두 시험군 모두 도메인 98, `SUBNET` 검색 및 루프백 UDP 프로필을 사용하고 한쪽에만 SHM 전송을 추가해 교대로 3회씩 기동했다. SHM 사용 시 0/3(모두 초기 위치 설정 75초 시간 초과), 미사용 시 3/3 준비됐다. 각 회차 AMCL과 smoother_server의 `/proc/<pid>/maps`로 SHM 사용 여부를 확인했다. 따라서 이 환경의 기동 실패는 SHM 전송 경로와 관련이 있다는 증거가 있지만, SHM 내부의 구체적인 결함이나 잔여 자원 등 정확한 원인은 미확정이다. 결과와 프로필: `docs/benchmarks/sim/dds-shm-compare-20261116/`; 원본 로그: `/tmp/jetinspect-dds-compare-2v3mvcv4/`.

Gazebo 전용 실행기·시험 도구는 공유 메모리를 끈 루프백 UDP 프로필을 사용한다. 시뮬레이션 실행기는 고정된 프로필 경로와 내용 및 격리 도메인을 검증한다. 이는 확인된 경로를 피하는 우회이며 Fast DDS 자체를 수정한 것은 아니다. 실제 로봇용 설정은 변경하지 않았다.

수정 후 `test_dashboard_gazebo.py --inspection-repeat`에서 격리 대시보드 API→독립 Gazebo/Nav2 기동→주행→경광등 점검을 3/3 성공했다. 세 회차 모두 빨강 on·노랑 off·초록 on이었고 각 색상 6표본을 관측했다. 실행기 단위 시험 11건과 격리 조건 시험 2건 통과. 실행 중 임무가 없을 때 대시보드 서비스를 재시작해 변경을 반영했고 임무 API 응답 200을 확인했다. 장시간 안정성과 실기 검증은 남았다.

### 추가 재현 및 시험 도구 수정
전체 임무 3회 재현에서 첫 회차는 주행 전 `gazebo_unavailable_or_unconfirmed`로 중단됐고 이후 2회는 성공했다. 실패한 회차의 Nav2 로그에서는 위치 추정 관리자가 활성화된 뒤 주행 관리자가 `smoother_server` 설정을 요청했으나, 서버가 `/smoother_server/change_state` 응답 전송 시간 초과를 경고하고 주행 관리자는 더 진행하지 않았다. 자동 스캔 매칭의 신뢰도가 부족해 초기 위치를 자동 설정하지 않은 것도 관찰됐지만, 별도 임무 실행기가 초기 위치를 보냈다. `/tmp/jetinspect-nav2-current-evidence/nav1.log`에 해당 로그를 보존했다(임시 파일).

설치된 Nav2 서비스 클라이언트 구현은 응답을 무기한 기다릴 수 있다. 서비스 응답이 전송되지 않아 주행 준비가 진행되지 않은 것은 관찰된 현상이지만, DDS 통신·자원 지연 등 **전송 실패의 근본 원인은 아직 확인되지 않았다**. AMCL 응답 시간 초과가 났던 이전 실패도 같은 원인이라고 단정하지 않는다.

수정: 시험 도구가 위치 추정 관리자의 `Managed nodes are active`만 보고 전체 Nav2 준비로 판단하던 문제를 고쳤다. 초기 위치 설정을 위해 임무를 시작한 뒤 두 관리자 각각의 준비를 확인한다. 실패 시 전체 Nav2/Gazebo 로그, ROS 노드·라이프사이클 상태와 시험 실행기 로그를 보존한다. Gazebo 실행기에서는 주행 Action 서버 부재를 `nav2_action_unavailable`로 구분해 관제 화면에 표시한다. 이 수정은 **서비스 응답 유실 자체의 해결책은 아니다**.

수정한 준비 기준에서 전체 주행·점검 3회 모두 성공했고 관련 단위 시험 11건과 관제 회귀 시험 34건이 통과했다. 간헐 오류가 다시 발생하지 않았으므로 통신 오류의 근본적인 해결이나 장시간 안정성을 주장하지 않는다.

## Gazebo 점검 중 브리지 중단 (2026-11-16)
`test_dashboard_gazebo.py --inspection-bridge-loss`로 격리 Gazebo 주행을 완료하고 점검 단계 진입 후 RGB 토픽의 실제 영상 헤더를 받았다. 해당 시험의 Gazebo launch 프로세스 그룹에 속한 `ros_gz_bridge` 하나만 종료하고 프로세스 종료를 확인한 다음 가상 대상의 위치를 카메라 관측 위치로 옮겼다. 임무는 `failed`, 사유 `inspection_unconfirmed`, 결과 없음으로 기록됐으며 시험 도구는 기대한 실패로 통과했다. 브리지는 카메라뿐 아니라 `/clock` 등도 중단하므로 카메라 단독 장애 시험은 아니다. 중단 후에는 영상을 확인할 수 없어 도착 자세에서 대상이 실제 시야에 들어왔는지도 독립적으로 확인하지 못했다.

첫 시도는 ROS 영상 확인 명령이 기대한 출력을 반환하지 않아 브리지를 중지하기 전에 시험 도구가 중단됐다. 별도 Gazebo 카메라로 출력 형식을 확인하고 메시지 타입을 명시한 뒤 재시험했다. 그 다음 시도는 대상 없이 중단해 위 결과와 같이 실패했으나 영상 중단과 대상 부재를 구분할 수 없었다. 최종 시험에서는 브리지 중단 후 대상을 배치하고 결과를 다시 확인했다.
