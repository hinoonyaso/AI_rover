# 음성 호출어가 인식되지 않는 현상

- 상태: 미해결, 음성 관제 시제품 인식 품질 개선 및 실제 발화 평가 필요.
- 증상: Piper 합성 발화 4개를 기존 로컬 Whisper base 한국어 모델로 시험했을 때 모두 `로버` 호출어가 정확히 전사되지 않아 명령이 무시됐다. 이 소수 합성 표본은 실제 사용자 인식률을 대표하지 않는다.
- 확인된 원인: 음량 VAD는 발화 구간만 분리하며 호출어 판정은 STT 출력의 정확한 접두어에 의존한다. STT가 호출어를 다른 단어로 출력하면 이후 해석 단계에 도달하지 못한다. 모델·발음·마이크·소음 중 어느 요인이 지배적인지는 아직 확인되지 않았다.
- 현재 동작: 화면의 인식 문장 확인과 텍스트 시험을 제공한다. 모의 임무는 별도 확인 후 실행되며 실제 구동 명령은 제공하지 않는다. 오인식을 무조건 호출어로 받아들이는 우회는 적용하지 않았다.
- 남은 검증: 사람 발화와 무음·주변 소음·스피커 재유입의 독립 음성 표본, 호출어 오탐/미탐과 지연을 측정하고 모델·별도 호출어 검출기 변경을 비교한다. 오탐이 없는지 확인하기 전까지 실기 제어에 연결하지 않는다.

## 추가 확인: Whisper 초기 프롬프트 효과와 오탐 (2026-11-22, Claude Code)

- Piper `ko_KR-kss-medium` 합성 → sox 16kHz 변환 → 기존 `whisper-cli` + `ggml-base.bin`, `-l ko`. 스피커 재생·로봇 구동 없음. 임시 파일은 세션 scratchpad에만 둠.
- 호출어 포함 6문장: 프롬프트 없이 호출어 정확 0/6(`노버`, `로봇`, `룰 볼`, `Z로봇` 등). `--prompt "로버, 제트로버. 로버 배터리 상태 알려줘. 로버 모의 점검 시작해."` 사용 시 호출어 6/6(본문 오인식 `나이다`, `뭐 이모 취소해`는 남음).
- 같은 프롬프트로 호출어 없는 4문장 + 핑크 잡음 3초: `모의 점검 시작해.` → `로버 모의 점검 시작해.`로 **호출어가 없는데 생성됨**(오탐 1/4). 잡음 → `이곳은 제트로버.`(현재 정규식 접두어와는 불일치하지만 환각).
- 결론: 미탐의 주된 원인은 base 모델의 고유명사 편향(프롬프트로 대부분 해소). 그러나 프롬프트는 오탐을 만든다. 프롬프트 단독 적용은 안전하지 않고, 별도 호출어 검출기(예: 마이크 어레이 내장 깨우기/KWS 모델)나 푸시투토크와 비교가 필요하다. 합성 음성 소표본이며 실제 사람 발화 성능이 아니다.
- 보조 관찰: `voiceVad.js`의 `MonoResampler`는 저역 통과 필터 없이 표본을 솎아내 48kHz→16kHz에서 앨리어싱이 생길 수 있다(브라우저 경로 전용, 이 실험엔 영향 없음). 정규식은 `제트 로버`(띄어쓰기)를 받지 않는다.

## 내장 호출어(R818 "Hello Hiwonder") 전환 시험 (2026-11-22)

사용자 결정: 전사 기반 호출어 대신 마이크 보드 내장 호출어 "Hello Hiwonder"만 사용한다.

- 도구: `tools/audio/r818_wake_probe.py`(수신 프레임 전체 기록, 음성 저장·로봇 구동 없음). 포트 `/dev/serial/by-path/platform-3610000.usb-usb-0:2.1.1.1:1.0-port0`(현재 `ttyUSB0`, 다른 프로세스 미사용 확인).
- 수신 전용 90초: 핸드셰이크 180회(0.5초 주기)만 수신, 사용자가 "Hello Hiwonder" 발화했으나 다른 프레임 0.
- 확인 응답(`--ack`) 90초: 핸드셰이크 3회 후 중단(연결 성립), "Hello Hiwonder" 3회 발화에도 프레임 0, 사용자 관찰상 보드 소리·LED 반응 없음.
- 제조사 자료(Elephant `mercury_speech`): 호스트는 포트에 쓰지 않고 `{"type":"aiui_event", "content":{"result","info"}}` JSON만 읽는다. Hiwonder 문서상 기본 호출어는 "hello hiwonder"이며 언어 전환은 Hiwonder 이미지의 GUI 도구/`xf_mic_asr_offline mic_init.launch.py`가 담당한다. 호출어 설정 시리얼 명령은 공개 자료에서 찾지 못함.
- 원인 후보(미확정): ① 보드에 다른 호출어(중국어 "小幻小幻" 등) 또는 빈 호출어 자원이 설정됨, ② 2026-11-11 보드 내부 프로세스 재시작 실험 이후 보드 음성 처리 상태 이상(당시 모노 음량 저하 기록, `prd/audio-doa.md`), ③ 이벤트 송신에 호스트 측 설정 명령이 필요.
- 다음 확인: 보드 내부를 ADB로 읽기 전용 확인(`vtn/vtn.ini`·호출어 자원·`demo.log`에서 발화 시 깨우기 로그) 또는 Hiwonder `xf_mic_asr_offline` 소스 확보. 이 확인 전에는 내장 호출어 기반 음성 관제를 구현 완료로 보지 않는다.

## 해결: 보드 호출어를 "Hello Hiwonder" 단독으로 설정 (2026-11-22)

- **원인 1**: ADB 읽기로 확인한 보드 로그(`/data/build/demo.log.before-array-probe`)의 과거 깨우기 이벤트 키워드가 `xiao3 huan4 xiao3 huan4`(小幻小幻). 보드 호출어가 중국어였다.
- **원인 2**: `hello hiwonder`로 바꿔도 반응 없음. `hiwonder`는 엔진 영어 사전에 없는 단어로 보이며(자원 사용량 928 → `hello hi wonder` 1969), 사전 단어 3개 `hello hi wonder`로 바꾸자 즉시 이벤트 수신. 발화는 그대로 "Hello Hiwonder".
- **방법**: 보드 펌웨어 `demo_vtn`이 시리얼 메시지(type 0x05) `{"type":"wakeup_keywords","content":{"keyword":"hello hi wonder","threshold":"500"}}`를 받으면 `ivw71_keyword_demo -content "<kw>;nCM:<th>|" -out /data/build/vtn/res.bin`으로 자원을 다시 만들고 `{"type":"wakeup_keywords","content":"keyword changed"}` 응답 후 약 30초 안에 음성 엔진을 재시작한다. 도구: `tools/audio/r818_set_wake_word.py`. 자원은 `/data`에 있어 재부팅 후에도 유지된다(이전 중국어 자원이 재부팅 후에도 유지됐던 것과 같음).
- **백업**: 원래 자원 `~/backup_r818_20261122/res.bin.xiaohuan`(MD5 `80e34bc0a970c434cbec0fe1c9b8f6da`) 및 보드 `/data/build/vtn/res.bin.xiaohuan-20261122`, `vtn.ini`·`user_cfg.ini`. 복구: 보드에서 `cp -p vtn/res.bin.xiaohuan-20261122 vtn/res.bin` 후 `demo` 재시작, 또는 설정 도구로 키워드 재설정.
- **이벤트 형식(실측)**: type 0x04, `{"type":"aiui_event","content":{"eventType":4,"info":"{\"ivw\":{\"angle\":..,\"score\":..,\"power\":..,\"beam\":..,\"keyword\":\"hello hi wonder\"}}","result":"hello hi wonder"}}`. 각도는 `info` 문자열 안 `ivw.angle`. 기존 `r818_doa.wake_angle`이 `info.angle`만 읽어 실제 이벤트를 놓치던 버그를 수정했다.
- **문턱값**: 900에서는 미검출, 500에서 검출. 수신된 점수 505~786. 두 번의 90/75초 시험에서 이벤트 6개·3개였으나 사용자의 정확한 발화 횟수가 기록되지 않아 미탐·오탐률은 미측정. 점수 505·507에 음량(power) 4.2·11.0인 이벤트는 오탐 의심. 보드 자체의 비프·LED 반응은 없고 시리얼 이벤트로만 확인된다.
- 2026-11-22 추가: 120초 5회 요청 시험에서 이벤트 4개(점수 506~845). 보드에 표시가 없어 사용자가 "인식 안 됨"으로 판단했던 것이므로 깨우기 확인음 도구 `tools/audio/r818_wake_listener.py`를 추가했고 사용자가 발화마다 비프음을 확인했다.
- **남은 검증**: 정해진 횟수 발화 + 호출어 없는 일상 대화·TV 소음 구간으로 미탐/오탐 측정 후 문턱값(예 500~600) 결정, 각도 영점·방향 보정, 웹 음성 관제와 연결(현재 웹 경로는 브라우저 마이크+전사 호출어).

## 로봇 마이크 경로 연결과 비프 잔향 오인식 (2026-11-22)

- 대시보드 서버에 R818 깨우기 → 보드 마이크 녹음 → Whisper → 제한 의도 경로(`tools/ops/backend/robot_voice.py`)를 추가. 실기(실제 보드·마이크·Whisper·스피커, 가짜 임무 저장소) 1차: 상태 조회 정상, "모의 점검 시작해" → `-뭐야.` 오인식.
- 2차(허용 명령 어휘를 Whisper `--prompt`로 제공): 상태 → 모의 점검 시작 → 확인 → 모의 임무 생성·시작 왕복 성공. 별도로 `[구독]`, `-뭐야.`×6 전사 2건 발생.
- 원인: 두 녹음은 1.2초·큰 프레임 4~6개, 최대 9,793으로 **로봇 스피커 비프음 잔향/잡음**이 발화 시작으로 잡혔고 Whisper가 잡음에 문장을 지어냈다(저장한 5개 녹음 분석).
- 수정: 비프 후 0.16초 버림, 큰 프레임 12개(0.24초) 이상만 발화로 인정, 괄호·반복 문장 환각 제거, 명령 미청취 시 음성 안내. 같은 5개 녹음 재생에서 잡음 2개 제외·명령 3개 유지.
- 전사 프롬프트는 호출어를 보드가 판단하므로 여기서는 호출어 오탐을 만들지 않는다. 잘못 유도돼도 확인이 필요한 모의 동작 대기까지만 생긴다.
- 각도: 4방향 보정(로봇 방위 = 기기 − 146°, 잔차 최대 약 15°)을 대시보드 기록에 반영(`prd/audio-doa.md`).
- 남은 것: 실제 운영 대시보드에서 사용자 종단 시험, 깨우기 오탐률, 소음·거리별 명령 인식률.
