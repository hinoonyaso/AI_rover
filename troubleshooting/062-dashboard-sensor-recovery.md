# 062. 관제 센서 복구 시험과 깊이 장애물 데이터 미수신 (2026-11-19)

- 주행과 팔 이동 없이 실제 센서 및 웹 관제 장애 복구를 시험했다.
- 깊이 카메라의 컬러 영상은 수신됐으나 sparse 장애물 점은 수신되지 않았다. 카메라 로그에는 팔 joint3이 홈 기준 약 0.205 rad 벗어나 depth cloud 발행을 차단한다고 기록됐다. 영상 수신이 장애물 감지를 뜻하지 않으므로 두 토픽 수신을 별도 표시한다. 홈 복귀 후 복구 여부는 미시험이다.
- LiDAR 중지 후 수신 만료는 정상. 첫 재시작에서 프로세스는 살아 있었지만 드라이버는 시작 메시지 이후 장치 정보와 스캔을 출력하지 않았다. 두 번째 재시작 후 장치 정보와 스캔이 복구됐다. 한 번 발생한 초기화 정체의 근본 원인은 미확정이며 반복 시험이 필요하다.
- 카메라는 중지 후 수신 만료, 재기동 후 영상 수신 복구를 확인했다. MySQL 재시작 전후 임무 2건·이벤트 10건 및 DB 연결을 확인했고 미리 DB 백업을 생성했다. 웹 서버는 재시작 후 HTTPS 복구했다.
- 사용자가 같은 네트워크의 다른 PC에서 HTTPS 로그인과 인증서 경고 없음을 확인했다. 센서 및 DB를 켠 60초 시험에서 HTTPS 정적 페이지 501회(오류 0, p95 0.070초), 서버 내부 상태 함수 115회(DB 오류 및 세 센서 미수신 0)를 확인했다. 인증된 HTTP API 다중 사용자나 장시간 시험 결과는 아니다.

## 추가 재현 및 검증 (2026-11-19)

- LiDAR 서비스를 연속 재시작한 결과 첫 2회는 약 7.1초에 수신이 복구됐지만 3회째에는 30초가 지나도 수신되지 않았다. 같은 실패를 디버거에서 2회 재현했다. 해당 시각 USB 재연결 커널 로그는 없고 장치 `/dev/ttyUSB1`은 열려 있었다.
- 설치된 `ros-jazzy-rplidar-ros` 2.1.0-4 / SDK 1.12.0에서 메인 스레드의 호출 경로는 `connect → checkMotorCtrlSupport → _waitResponseHeader → raw_serial::waitfordata`였다. 30초 이상 지난 시점에 응답 헤더 7바이트를 기다리면서 수신 큐에는 6바이트가 있었다. `waitfordata`의 호출 스택과 디스어셈블에서 이 부분 수신 상태의 대기 루프가 관찰됐다. 시간 제한을 넘기는 드라이버 대기 문제가 확인됐지만 왜 1바이트가 부족했는지는 미확정이다. 드라이버 재시작으로 복구했으며 자동 재연결이나 원인 수정은 적용하지 않았다.
- 사용자가 공간과 전원 스위치를 확인한 뒤 팔 joint3만 5초에 걸쳐 1.8724→1.6671rad(목표 1.6629rad)로 이동했다. 바퀴 명령 토픽은 별도 이름으로 분리했고 e-stop 해제를 비활성화했다. 이후 읽기 전용 모드를 복원했고 실제 깊이 장애물 점은 약 7.4Hz로 돌아왔다. 이는 토픽 수신 복구이며 장애물 인식 정확도 검증은 아니다.
- 운영 계정과 서비스를 수정하지 않은 임시 인증 서버(동일 앱 코드, HTTPS, 실제 ROS 스냅샷과 MySQL 사용, 앱 수명주기 비활성)에서 조회자 세션 4개로 300초간 `/api/status` 1,406회, HTTP/DB/센서 미수신 오류 0, p95 0.192초, CPU 최대 50.8%, RAM 최대 66.5%, 스왑 최대 41.5MiB를 기록했다. 이 5분 시험 당시 팔 홈 이탈로 depth cloud는 미수신 상태였으며 실제 운영 프로세스의 장시간 시험이나 원격 PC의 부하 시험은 아니다. 비인증 401, viewer의 센서 종료 403을 확인했다.
- 별도 인증 HTTPS 서버에서 운영 DB를 중단하면 `/api/status.database`가 `unavailable`, 재시작 후 `connected`로 복구됨을 확인했다. 임무 2건·이벤트 10건이 유지됐다. DB 백업 파일은 `~/.local/share/jetinspect-ops/backups/`에 보관돼 있다.
- 홈 복귀 후 추가 60초: 깊이 장애물 점까지 포함한 센서 수신과 인증 HTTPS 상태 조회 280회, 오류·미수신 0, p95 0.204초, CPU 최대 40.0%, RAM 최대 67.1%, 스왑 최대 41.5MiB.
- ROS 센서 서비스 전환 중 `get_parameters` 비동기 요청이 응답 없이 남으면 모니터가 후속 조회를 계속 건너뛰는 문제가 확인됐다. 5초가 지나면 요청을 취소하고 재시도하며 늦은 응답은 무시하도록 수정했다. 격리 회귀 테스트 2건 및 실제 팔 읽기 서비스 재시작 22초 뒤 매핑·관절·깊이 데이터 복구를 확인했다.
- 1시간 추가 부하 시험: 독립 사용자 서비스 `jetinspect-web-stability-20261119`로 시작, 결과 `~/.local/share/jetinspect-ops/soak/web-stability-20261119.log`. 실제 완료 결과 확인 전까지 장시간 통과로 표시하지 않는다. 배터리 10V 미만 시 중단한다.
- 1시간 인증 조회 시험 완료: 3,600초, 세션 4개, HTTPS 상태 조회 16,936회, HTTP·DB·IMU·LiDAR·영상·깊이 미수신 오류 집계 0, p95 0.186초, CPU 최대 82.8%, 메모리 최대 69.4%, 스왑 최대 93.2MiB. 일부 구간 RAG 평가가 병행됐다. 운영 서버가 아니라 임시 인증 서버에서 실제 센서와 DB를 읽었다.

## LiDAR 시작 정체 자동 복구 (2026-11-22)

- `jetinspect-lidar.service`가 드라이버를 직접 실행하던 것을 감시기 `tools/lidar/lidar_watchdog.py`를 거쳐 실행하도록 바꿨다. 드라이버를 자식 프로세스 그룹으로 띄워 `/scan`을 구독하고, 15초 안에 첫 스캔이 없거나 5초 이상 끊기면 드라이버를 재시작한다(최대 3회, 정상 60초 후 횟수 초기화, 이후 실패 종료 → 대시보드에 실패 상태 표시).
- 실기: 서비스 시작 첫 실행이 `Start` 로그 전에 멈춤 → 15초 후 감시기 재시작 → 두 번째 실행 `/scan` 13.7Hz. 이어서 서비스 재시작 5회 모두 스캔 복구(감시기 재시작 0회 필요). 중지 시 코어 덤프(rclpy 기본 신호 처리기와 스핀 스레드 충돌)를 수정해 정상 종료 확인.
- 함께 확인한 것: LiDAR 전원이 꺼져 있어도 USB 변환기는 열려 드라이버가 `Start`까지 출력하고 데이터만 없다. 감시기는 이를 같은 장애로 보고 재시작하므로 로그 문구에 "LiDAR power/cable"을 함께 표시한다. 1바이트가 모자라는 근본 원인은 여전히 미확정이며 재시작으로 회피한다.
